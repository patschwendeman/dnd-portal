# Domäne & Begriffe

| Begriff (fachlich) | Bedeutung | Im Code |
|---|---|---|
| Abenteuer | Oberste Ebene: eine Kampagne bzw. ein Abenteuer mit eigenen Szenen und Spielern | Tabelle/Model `Adventure` (Backend), API `/adventures`, Schemas `AdventureSummary`/`AdventureDetail`; Szenen und Spieler gehören je zu genau einem Abenteuer (`adventure_id`); aktiv ist eines je Spieltisch (`game_table.active_adventure_id`, `PATCH /table`); im Frontend: Auswahl im Admin (Abenteuer-Auswahl im Panel „Einstellungen“, Name in der Kopfzeile), `activeAdventureId` im `ActiveAdventureContext` (aus dem WebSocket-Snapshot) |
| Spieltisch | Der gemeinsame Zustand von Admin, Wall und Ground: aktives Abenteuer, dessen aktive Szene, Theme, Wall-Overlay und Ground-Raster; ein Server = ein Spieltisch. Die Player Screens sind ebenfalls verbunden, übernehmen aber nur das Theme | Tabelle/Model `GameTable` (`game_table`, genau eine Zeile), API `GET`/`PATCH /table` (`GameTableState`, `GameTableUpdate`), WebSocket `/ws` (Snapshots); im Frontend `GameTableProvider`/`useGameTable` (`src/realtime/`) |
| Theme (global) | Farbschema „Cyber“ (`cyber`) oder „Taverne“ (`tavern`) der Spieltisch-Screens, im Admin gewählt (Panel „Einstellungen“); unabhängig vom Abenteuer, ein Wechsel ändert nur die Farben | `game_table.theme`, `GameTableState.theme`, Frontend-Typ `Theme`, Paletten `cyberTheme.ts`/`tavernTheme.ts`; der Player Screen übernimmt es, ein Spieler kann auf seinem Gerät abweichen (`localStorage` `playerThemeOverride`) |
| Abenteuerbild | Bild eines Abenteuers, das in jedem Theme abgedunkelt hinter den Kacheln des Admins und den Karten von Charakterauswahl und Player Screen liegt; wechselt nur mit dem Abenteuer | `adventure.image_media_id` → `Media`, API `AdventureDetail.image` (`Image \| null`); festgelegt per Seed bzw. Migration, im Admin nicht wählbar; im Frontend `adventureBackgroundSource`, `useAdventureBackground`, `AdventureBackground` |
| Spielleiter / Admin | Erzählt die Geschichte, spielt alle NPCs, steuert die App | Route `/admin`, `AdminScreen` |
| Spieler | Spielt einen Charakter, nutzt den Player Screen | Route `/` (`PlayerScreen`) |
| Spieler / Charakter (Datenmodell) | Eine Person mit ihrem Charakter in einem Abenteuer; in einem anderen Abenteuer hat dieselbe Person einen eigenen Eintrag | Tabelle/Model `Player`: `player_name`, `character_name`, `race`, `character_class` (Freitext; `class` ist in Python reserviert), optional `avatar` (`Media`); API-Schema `Player` in `AdventureDetail.players` |
| Globales Level | Charakterlevel, das vorerst für alle Spieler eines Abenteuers gilt (1–20) | `Adventure.global_level` (Default 1) |
| Aktive Szene | Szene, die der Spielleiter gerade aktiviert hat und die Wall und Ground zeigen | Im Frontend `activeSceneId` (`number \| null`, `null` = keine Szene aktiv) im `ActiveSceneContext` (aus dem WebSocket-Snapshot, `GameTableState.active_scene_id` = aktive Szene des aktiven Abenteuers); persistent im Abenteuer: `Adventure.active_scene_id` (`PATCH /adventures/{id}`, nur Szenen desselben Abenteuers), beim Aktivieren gespeichert |
| NPC | Nicht-Spieler-Charakter, freundlich oder feindlich, vom Spielleiter gespielt | kein eigenes Datenmodell (kein NPC-Katalog); Infos in Markdown-Notizen; im Kampf nur als Kampfteilnehmer `enemy`/`ally` mit Nummer und Bezeichnung |
| Kampf | Läuft in der Szene, in der der Spielleiter ihn startet; höchstens einer je Abenteuer, bis „Kampf beenden“. Solange er läuft, lassen sich Szene und Abenteuer nicht wechseln. Der Admin zeigt ihn, die Wall als Initiative-Leiste ohne die Bezeichnungen der NPCs, der Player Screen „Am Zug“ und „Zug beenden“ für den eigenen Charakter (Ground noch nicht) | Tabelle/Model `Fight` (`fight`: `adventure_id` unique, `scene_id`, `round`, `active_combatant_id`), API `/table/fight` (`FightState`), WebSocket-Nachricht `fight` an Admins, Walls und Player (an Walls und Player `label: null`); im Frontend `FightContext`, Menüpunkt und Panel „Kampf“ (`FightPanel`), Dashboard-Panels „Am Zug“ (`TurnPanel`) und „Initiative“ (`InitiativePanel`), auf der Wall `WallInitiative`, im Player Screen `PlayerHeroCard` |
| Kampfteilnehmer | Ein Spieler des Abenteuers oder ein NPC (Gegner, Verbündeter) im Kampf; kann ausgeschieden sein (Spieler „Tot“, NPC „Besiegt“) und wird dann beim Zugwechsel übersprungen | Tabelle/Model `Combatant` (`combatant`: `kind` `player` \| `enemy` \| `ally`, `player_id` nur bei Spielern, `defeated`), API-Schemas `Combatant`, `CombatantCreate` |
| Initiative | Reihenfolge, in der die Kampfteilnehmer am Zug sind; der Spielleiter legt sie per ↑/↓ fest (keine Initiativewerte) | `combatant.position`, `PUT /table/fight/order`; Frontend `FightState.combatants` (in Reihenfolge) |
| Zug / Runde | Am Zug ist ein Kampfteilnehmer; „Zug beenden“ gibt den Zug an den nächsten nicht ausgeschiedenen weiter, über das Listenende hinaus beginnt die nächste Runde (Start: Runde 1, erster Teilnehmer) | `fight.active_combatant_id` (`null` = niemand am Zug), `fight.round`, `POST /table/fight/turn` (`from_combatant_id`) |
| Nummer (NPC) | Nummer der Figur auf dem Tisch, 1–99, eine gemeinsame Zahlenreihe für Gegner und Verbündete; belegt, solange der Teilnehmer in der Liste steht. Dazu optional eine Bezeichnung („Ghul“), die nur der Spielleiter sieht | `combatant.number`, `combatant.label`; Frontend `smallestFreeNumber`, `numberError` (`src/utils/fight.ts`) |
| Szene | Situation, die der Spielleiter aktiviert (Dorf, Shop, Taverne, Kampfschauplatz …); bündelt Wall-Bild, Ground-Bild und Musik. Alle Szenen sind gleich: Ob gekämpft wird, entscheidet nicht die Szene; ein Kampf lässt sich in jeder Szene starten (siehe Kampf) | Tabelle/Model `Scene` (Backend), API-Schema `SceneDetail` (Backend `app/schemas/`, Frontend-Typ generiert), `GET /adventures/{id}/scenes`; im Admin Panel „Szenen“ (`SceneNavigation`) |
| Wall-Bild | Atmosphäre-Hintergrund der Szene | `Media` (`kind` `image`) / `scene.wall_image` |
| Ground-Bild | Spielbrett/Kampfschauplatz der Szene (Bild oder Video) | `Media` (`kind` `image`) / `scene.ground_image` |
| Musik (Sound-Element einer Szene) | Playlist von Tracks einer Szene, vom Server zufällig gewählt und von der Audioausgabe abgespielt; ohne aktive Szene die Standardmusik | `Media` (`kind` `audio`), n:m über `scene_track`; `scene.tracks[]` (API-Typ `Track`); Musikzustand im Speicher des Servers (`AudioService`, `app/realtime/audio.py`), API `GET`/`PATCH /table/audio` (`AudioState`, `AudioUpdate`), Standardmusik `Settings.default_music_key` |
| Soundeffekt | Einzelner Sound, den der Admin manuell auslöst (Heilung, Buff, Zauber …) und die Audioausgabe abspielt | `POST /table/sounds` (`SoundRequest`, Name `SoundName`), WebSocket-Nachricht `sound`; Liste im Frontend `src/audio/sounds.ts` (Icons im Panel „Audio“, Dateien in `public/assets/sounds/`) |
| Audioausgabe | Das Admin-Fenster, das Musik und Soundeffekte abspielt; immer höchstens eines (ohne Ausgabe wird es das Admin-Fenster mit der nächsten Nutzerinteraktion, Klick oder Tastendruck); den Lautsprecher wählt der Spielleiter außerhalb der App | WebSocket-Nachrichten `audio_ready`, `audio_output`, `track_ended` (nur von bzw. an `screen=admin`); `AudioState.output_ready`; im Frontend `AudioPlayer` (`src/audio/audioPlayer.ts`), `useAudioPlayback`, `useAutoAudioOutput`, `GameAudioContext` |
| Notizen | Markdown-Dateien zu Story, NPCs, Kämpfen, Leveling, Regeln; untereinander per Querverweis verlinkt | nur Frontend: `public/story/<ordner>/*.md`, Einträge im Panel aus dem Verzeichnis `NOTE_FOLDERS` (`src/notes/noteFolders.ts`), Anzeige `DocumentReader`, Querverweise als Markdown-Links auf `.md`-Dateien (`resolveNoteLink`), Verlauf `useNoteHistory` |
| Ressourcen (Spieler) | Aktion, Bonusaktion, Zauberplätze I–IV, Spezial-Ressource (+ WIP: Bewegung) | nur Frontend: `ResourceBarPlayer` (lokaler State) |
| Grid / Ground-Raster | Optionales Raster auf den Ground Screens für taktische Kämpfe: Linienfarbe Schwarz/Weiß oder aus, Zellgröße 100–200 (Schritt 10); Teil des Spieltischs, vom Admin umgeschaltet (Farbe im Panel „Spieltisch“, Zeile „Ground“; Zellgröße im Panel „Einstellungen“), gilt für alle Grounds und bleibt bei Szenen- und Abenteuerwechsel | `GameTableState.ground_grid` (`"black"` \| `"white"` \| `"off"`) (nur im Speicher der API: `app/realtime/ground_grid.py`) und `ground_grid_cell_size` (Spalte `game_table.ground_grid_cell_size`), Frontend-Typ `GroundGrid`, `groundGrid`/`groundGridCellSize` im `GameTableContext`, `GridOverlay`, Panels `GameTablePanel` und `SettingsPanel` |
| Wall-Overlay | Was die Walls über dem Szenenbild zeigen: die Weltkarte, den QR-Code für die Spieler oder nichts; Teil des Spieltischs, vom Admin umgeschaltet (Panel „Spieltisch“: Weltkarte und Aus in der Zeile „Wall“, QR-Code per Icon-Button in der Zeile „Spieler“), ein Szenen- oder Abenteuerwechsel schaltet es aus | `GameTableState.wall_overlay` (`"world"` \| `"join"` \| `"off"`, nur im Speicher der API: `app/realtime/wall_overlay.py`), Frontend-Typ `WallOverlay`, `wallOverlay` im `GameTableContext`, Panel `GameTablePanel` |
| Weltkarte | Overlay auf dem Wall Screen (Wall-Overlay `world`) | WallScreen: statisches Bild (`mapOverview.jpg`), Button „Weltkarte“ im Admin |

## Historische Bezeichnungen

- Kampfszene / Nicht-Kampfszene (`Scene.main` `true`/`false`, „Mainmap“/„Sidemap“, Endpoints
  `/adventures/{id}/maps/main|side`, Wall-Overlay „Kampfschauplätze“ mit Button BATTLE): seit DND-29 entfernt, alle
  Szenen sind gleich. Die Bezeichnungen bleiben nur in Asset-Pfaden: `music/main/`, `music/side/`,
  `images/ground_screen/main_N.jpg`, `images/wall_screen/fight.jpg`.
- Davor: `battlemap(s)` → `mainmap(s)` bzw. `main` (Commit „Change battlemaps to mainmaps“), `sidemap(s)` → `side`,
  `fight` (Bool auf Scene) → `main`.
- `v1-roguelike` (Tags `archive/*-v1-roguelike`): altes, **verworfenes** Konzept mit Tabelle `battlemaps` (loot, xp, enemies, locked,
  source_locked) und PUT-Endpoint zum Entsperren. Im Code sind keine Reste mehr vorhanden.
